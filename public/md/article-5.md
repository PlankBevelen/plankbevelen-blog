## http

首先了解什么是HTTP，http基于TCP/IP协议的一种应用层协议，用于客户端和服务器之间的通信。（发展后又要弹区别了，因为http3它基于UDP）其核心构造为两部分：请求报文、响应报文。

请求报文：

- 请求行：请求方法+请求URL+HTTP版本
- 请求头：键值对，描述请求的一些信息
- 空行：请求头和请求体之间的空行，用于分隔。比如：'/r/n'
- 请求体：可选，用于POST、PUT等方法，包含要发送的数据

响应报文：

- 状态行：HTTP版本+状态码+状态描述
- 响应头：键值对，描述响应的一些信息
- 空行：响应头和响应体之间的空行，用于分隔。比如：'/r/n'
- 响应体：可选，包含服务器返回的数据（JSON啊、HTML啊什么的）

然后就是http的发展，它每个版本到底做了什么，有啥特点，版本更新到底更新了什么。

### http发展

从0.9、1.0、1.1、2.0、3.0等版本挨个说。

#### 0.9 版本

只有get方法，甚至没有http头部，只能请求数据，不能发送数据。
太简单了，简单到没有多余的操作，眼里只有拿到数据资源的欲望，拿了就分手。
所以优缺点很明显：传输速率快，且只拿不给，没有缓存。同样因为它只拿HTML数据，就不拿其他的，比如图片、CSS、JSON等非HTML数据。

#### 1.0 版本

1.0属于是开了智了，1.0版本在0.9版本的基础上：
- 添加POST、PUT、DELETE等方法(就是为了给服务器发送数据)
- 引入http头部（响应头/请求头），支持 content-type（资源格式）、Authorization（认证信息）、cache-control（缓存控制）、user-agent（用户代理）等。
- 加了状态码，这个时候还比较简单，只有200、404、500等。
- 引入了cookie，用于在客户端和服务器之间进行状态管理。

所以他的特点是基于0.9的缺点，支持了数据提交、多种资源获取、状态码、cookie等。
一代有一代的缺点，想法是好的，实施起来还是有很多问题，说白了就是没有考虑性能。
【队头阻塞】：同一 TCP 连接中，请求按顺序执行，其实就是请求全部塞队列了，挨个买单
除了挨个结账，还出现了个问题，默认一个请求对应一个TCP连接，这就导致了如果一个页面有多个资源，就会出现多个TCP连接，这就导致了资源的加载效率低。
还有就是头部信息的重复传输，每个请求都要携带相同的头部信息，这就导致了资源的传输效率低。

#### 1.1 版本

就是为了解决性能问题，赶紧搞了1.1出来。
1.1版本在1.0版本的基础上：
- 默认开启，持久连接（keep-alive），可以在一个TCP连接上发送多个请求，而不是每个请求都建立一个新的连接。
- 支持 Pipelining：一个TCP连接可以并行发送多个请求，而不是挨个买单了。
- 加了请求头字段：Host（主机名）、Connection（连接状态）、Cache-Control（缓存控制）、ETag/If-None-Match
- 加了状态码，100预处理、409 资源冲突、 503 服务不可用（服务器暂时无法处理请求，可能是因为维护、升级等原因）
- 支持 Chunked Transfer Encoding（分块传输编码）：可以在传输大文件时，将文件分成多个块，每个块都有自己的长度，客户端可以边接收边解析，而不是等待整个文件接收完成。

看似完美，依旧有缺点，队头阻塞没有完美解决，只是说可以并行发送请求了，但是没有说可以同时处理响应啊。
因为每个请求都要等待前一个请求的响应，才能处理下一个响应。有个问题没解决，头部冗余问题。并行发送请求的个数也有限制，一般是6个。

#### 2.0 版本

我的评价是，谁点的魔王护

- 【二进制协议】：将请求 / 响应拆分为二进制帧（Frame），而非 ASCII 文本（减少解析开销，支持并行处理）
- 【多路复用】：一个TCP连接里面，多个请求 / 响应 通过不同的帧ID并行传输，彻底解决队头阻塞问题
- 【头部压缩】：对重复的头部字段进行字典编码（如 Host、Cookie），减少头部传输体积
- 【服务器推送】：服务器可以主动向客户端推送资源，而不需要客户端请求。（比如：客户端请求HTML页面，服务器同时推送CSS、JS、图片等资源）
- 【流控制】：每个流都有自己的优先级，服务器可以根据优先级调整流的传输顺序，避免某个流占用过多带宽导致其他流阻塞。（比如，指定HTML优先传输，因为HTML是用户可见的，而图片、CSS、JS等资源是用户不可见的，所以HTML优先传输可以提高用户体验）

好处说完了，那坏处呢？
没有摆脱TCP的坑，TCP层的队头阻塞还在啊，只要丢一个包，整个连接的帧都得等待重新传；而且主流的浏览器（这个地方我被找过问题，Chorme高一点版本访问不到不到http://plankbevelen.cn，会出错，为啥，我nginx没有配置SSL证书），只支持 HTTPS 版的 2.0，得配 SSL 证书，部署成本高；服务器推送还容易「瞎推送」，客户端缓存里有的资源还推，白浪费带宽。

我只能说老板是个三千，被TCP耽误了

#### 3.0 版本

3.0 知道 2.0 老板是个三千了，换了家俱乐部，底层抛弃 TCP，改用 UDP（QUIC 协议）：
- 0-RTT 连接：首次连接 1 次往返就能建，后续重连直接 0-RTT，不用三次握手，连接速度快到离谱，移动端切换 WiFi/4G 都不卡
- 彻底解决队头阻塞：QUIC 的流是独立的，一个流丢包，其他流照样传，不会牵连 —— 就像快递，一个包裹丢了，不影响其他包裹派送
- 内置 TLS 1.3：强制加密，不用额外配 SSL，安全性拉满，还省了部署成本
- 连接迁移：客户端换 IP / 端口（比如手机从 WiFi 切到 4G），连接还能续用，不用重新登录、重新加载，体验丝滑到哭

又到了缺点环节：兼容性问题，旧点的浏览器不认这个，部署得升级最新版本（比如 Nginx 要编译特殊模块）；调试也贼麻烦，二进制帧 + QUIC 协议，传统抓包工具根本看不懂

#### 总结

- 0.9：古董，只存在于教科书
- 1.0：凑活，老系统才用
- 1.1：主流，兼容性拉满，日常用够了
- 2.0：优选，配 HTTPS 就升，性能提升立竿见影
- 3.0：前瞻，等兼容性普及了再冲，移动端 / 高并发场景优先尝鲜

### GET POST 区别

参数长度，get一般在2048字符左右，post没有长度限制。
传输方式，get是明文传输，post是放在请求体中的。
缓存，get请求会被浏览器缓存，而post请求不会（post可以在请求头中设置cache-control: max-age进行缓存，expires: 过期时间）
处理，get一般是请求数据，post一般用于更新、删除、新增数据。

### 状态码

#### 2xx 成功问题

- 200 OK：请求成功，返回请求的数据。
- 201 Created：请求成功，并且创建了新的资源。（一般是提交）
- 204 No Content：请求成功，但是没有返回数据。（一般是删除操作）
- 206 Partial Content：请求成功，返回部分数据。（一般是视频、音频等大文件的播放）

#### 3xx 重定向问题

- 301 Moved Permanently：请求的资源已经被永久移动到新的URL，后续请求应该使用新的URL。
- 302 Found：请求的资源临时移动到新的URL，后续请求应该使用新的URL。
- 303 See Other：请求的资源临时移动到新的URL，后续请求应该使用新的URL。（与302不同的是，303会强制将请求方法改为GET）
- 304 Not Modified：请求的资源未被修改，返回空体。（一般是缓存）
- 307 Temporary Redirect：请求的资源临时移动到新的URL，后续请求应该使用新的URL。（与302不同的是，307会保留请求方法和请求体）

#### 4xx 客户端问题

- 400 Bad Request：请求参数错误，服务器无法理解。
- 401 Unauthorized：请求需要用户认证，用户未认证。（一般是缺Token）
- 403 Forbidden：服务器拒绝请求，用户认证成功但是没有权限。（权限不够，怎么样都不给看）
- 404 Not Found：请求的资源不存在。
- 405 Method Not Allowed：请求方法不被允许，比如get请求一个post接口。
- 408 Request Timeout：请求超时，服务器在规定时间内没有收到请求。
- 413 Payload Too Large：请求体过大，服务器无法处理。
- 414 URI Too Long：请求的URI过长，服务器无法处理。
- 429 Too Many Requests：请求频率过快，服务器拒绝处理。（限流）

#### 5xx 服务器问题

- 500 Internal Server Error：服务器内部错误，无法完成请求。
- 502 Bad Gateway：网关错误，服务器作为网关或代理，从上游服务器收到无效响应。
- 503 Service Unavailable：服务器暂时无法处理请求，可能是过载或维护。
- 504 Gateway Timeout：网关超时，服务器作为网关或代理，但是没有及时从上游服务器收到响应。

#### 301 与 302 与 303 与 307 区别

- 301 会告诉浏览器，目标资源搬家了，浏览器会记住新家，后续找人去新家找。（比如nginx，你配置个http://nihao.com，再配置个return 301 https://nihao.com;）
- 302 同样告诉浏览器，目标资源搬家了，但是浏览器不会记住新家，后续继续找原来的地址。（比如你在浏览器输入http://nihao.com，服务器返回302，浏览器会继续找http://nihao.com，而不是https://nihao.com）
- 303 告诉浏览器，目标资源搬家了，但是浏览器会记住新家，后续继续找新家。（对标301，用户注册post成功后跳转get成功页面）
- 307 告诉浏览器，目标资源搬家了，但是浏览器不会记住新家，后续继续找原来的地址。（对标302，比如你请求/api/v1/nihao，保留参数带到/api/v2/nihao）

以http版本划分，302、301是http/1.0的，303、307是http/1.1的。303、307出现就是为了解决301、302的问题，301、302未强制要求保留原方法，但几乎所有浏览器会把 POST 请求转为 GET，所以就出现了303、307，303会强制将请求方法改为GET，307会保留请求方法和请求体（post还是post，put还是put）。
